# 全体方針
研究は「人間」「計画AI(Webブラウザ版のAI)」「作業AI(CLI版のコーディングエージェント)」の3主体で回す。
良い研究をするには、オープンな姿勢が重要。 **忌憚なく意見を言い合う**こと。




## 人間と計画AIがやること
* 研究計画の立案
    - より具体的には、[研究の設計](./research_design.md)を行い、それを[研究計画書](#研究計画書)にまとめる。
* [先行研究調査](./literature_review.md)




## 作業AIがやること
[実装](#実装)や[実験](#実験)といった実作業を行う。
作業内容は、基本的には[研究計画書](#研究計画書)に従う。

作業を効率的に進めるための工夫をする。例えば以下を含む:
* できる限りのところまで、自律的に作業を進める。このために、些細な事項に関しては裁量判断する。
* 作業は可能な限り並列で行う。
* [実験サイクル高速化](./experimental_design.md#実験サイクル高速化)に従う。

作業ブランチはhonoka-devとする。
commitの単位はある程度大きくてよい(例: 実験のための一連の実装、一連の実験の完了、等)。
ただし、大きな変更の場合は別ブランチで実装し、`--no-ff`オプション付きでhonoka-devブランチにマージする。
自律的にどんどんcommitとpushをしていく。









# 研究計画書




## 概要
* 研究計画の全てを記した文書。研究は基本、この計画書に従って進めることになる。
    - ただし、この計画書にとらわれすぎずに、裁量判断することも重要である。
        * 例) 「データセットの難易度はもう少し高い方が良い」「この工程はスキップしても問題なさそう」「データ数を限って試行錯誤した方が早そうだ」等。
    - また、計画書を読んでいて気がついた点があれば、常にどしどしと挙げる。
* 指示されたタイミングで更新する。更新は、単なる情報の追記ではなく、文書をあるべき姿(下記)に保つための「推敲と改訂」である。更新したら、commit & pushする。
    - 編集時は[分かりやすい返答のための一般論](https://github.com/HonoMi/AI-instructions/blob/honoka-dev/good_writing.md)に従うこと。

以下、書き方を説明していく。




## 本文 ("main.md")
* 正しい姿は、現時点の研究の状態において、[研究の設計](./research_design.md)、つまり「問いから主張の回収まで」が一貫して、論理的に、**簡潔に**述べられており、かつ、それ以外の情報が存在しない状態である。よって、編集は、例えば以下のような方針を含む:
    - 「論理を追うのに必要無い詳細な情報」「過去の経緯・紆余曲折」「既に捨てた提案手法とその結果」などは書かない。こういったものは、付録か古文書に書く。
    - 他の文書に書かれていることは、書き直さず、その文書への参照と簡潔な説明だけにとどめる。
    - 文章量が増えすぎた場合、別文書にまとめ、引用する。
    - 図表を見れば書いてある数値をいちいち引用しない。
    - 先行研究との詳細な差分は、[先行研究調査](./literature_review.md)に回す。
* 章立て: 文書のタイトル(例: `# 研究計画`)は書かずに、以下の章を直接書き始める。
    - [研究の設計](./research_design.md)に記載された各章 (直接これらの章を書き始めること。)
    - 「次の作業」という章
        * 適当な粒度の作業ごとに節を作り、優先度順に並べる。
        * **できるだけ一度に扱う作業範囲を増やす。** より具体的には、次に「人間・計画AIの判断が必ず必要になりそうな重大事項」が生じそうなところまでは全て、作業AIが自律的に進められるようにする。
        * 以下の作業を最後に含める: 「全て終わったら[レポート](#レポート)を書き、commitとpushをする。ただし、『次の作業』の提案は含めなくてよい。」
        * 作業が実験を含む場合は[実験設計](./experimental_design.md)に従う。




## 付録 ("appendix.md")
本文に載せられなかった情報を書く。

載せる情報は例えば以下である:
* 「将来もしできればでいいので、やりたい事項」("[future]"に区分けされた事項)
* 改訂履歴
* 過去の経緯
    - ただし、現在の研究を解釈する上で重要となるものに限る。そうでないものは「古文書」に移す。

文書のタイトルは書かずに、直接、「付録A」から書き始める。




## 古文書 ("old.md")
過去の経緯を書く。
基本は、main.md / appendix.md から「はみ出た」事項を追加していけばよい。
読むことは少ないので、推敲・改訂は不要。








# 実装
* `pyenv virtualenv`で環境を作る。
* `tqdm`でスクリプトの進行状況を表示する。
* `*.pyc` / `__pycache__`を作ったら消す。
* コミットメッセージのタグは以下とする:
    - `[update]`: 通常の更新。多くはこれ。
    - `[add]`: ファイルを追加。
    - `[remove]`: ファイルを削除。
    - `[refactor]`: リファクタリング。
    - `[save]`: 重大な変更前にコードを保全する。あまり使わない。
    - `[WARNING]`: 重大な変更。あまり使わない。








# 実験




## 全体方針
* 定期的に、作業完了までにかかる時間を見積もり、長時間(=5時間以上)かかりそうなら工夫を追加すること。例えば以下である:
    - プログラムを高速化する
    - データを分割して並列に処理する
    - 計算リソースを調整する(下記)




## ジョブ管理
* ジョブは一定の間隔(30分程度)で監視し、問題が起きていないか確認する。
* リソースの割り当ては基本的に以下とする:
    - GPUジョブ: `xhn_s.middle` (H100 x 2) / `xhn_s.small` (H100 x 1)
    - CPUジョブ: 軽い処理はホストノードでそのまま実行する。重い処理は `xcs.small` / `xcs.middle`
    - ただし、時間短縮のために、適宜リソース調整をする:
        * 長時間(5時間以上)かかりそうなジョブは、より大きなリソースへの変更を検討する
            - リソース一覧: `xhn_s.middle2` (H100 x 4) / `xhn_s.large` (H100 x 8)
            - ただし、大きなリソースは、待ち時間も多くなる可能性があることに注意。
        * 小規模ジョブは、`xhn_dev`を検討する。空きがある限り即座に実行に移るため。`xhn_dev`の仕様は以下である:
            - リソース: `xhn_dev.middle` (H100 x 2) / `xhn_dev.small` (H100 x 1)まで入る。ただし、全ジョブ合計で、同時に4GPUまでしか確保できない。
            - 上限時間: 4時間








# レポート




## 本文書の位置づけ
* ある程度個別のトピックに関してまとめる。




## 書き方
* 指示されたタイミングで執筆する。執筆したら、commit & pushする。
* self-containedに読めるようにする。このために、背景から今回の議論までを一貫して含める。
* ファイル名: `report.2026-10-19.<今回の内容を端的に表す>.md`
* **簡潔に**書く。
    - 詳細情報は、付録の章に移す。
